# 8/25 育成講師向け研修 受講生対応（想定問答集＋コードレビューTips）

> `docs/trainer_workshop_brief.md`コマ4で使う。対象は「実際の3日間クラスで受講生から聞かれる質問・相談」への対応方針。
> `docs/trainer_workshop_content.md`のA・B項目（育成講師自身の理解のため）とは目的が異なり、こちらは**受講生に対してどう振る舞うか**の型を渡すためのもの。

## 想定問答集：拾う質問／触れる程度／後回しにする質問

質問の性質ごとに対応方針を分けて渡す。「全部丁寧に答える」姿勢は美徳に見えるが、他の受講生の時間を奪い、`docs/agenda.md`のスケジュールを崩す原因になる、という前提を最初に共有する。

### カテゴリ1：カリキュラム範囲内の技術的質問 → **拾う（その場で答える）**

`docs/trainer_workshop_content.md` A項目の内容がそのまま使える。

| 想定質問                                                           | 対応の芯                                                               |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 同じclassの要素が複数あるのに`querySelector()`で書いたらどうなる？ | 最初の1件だけ返る。複数扱うなら`querySelectorAll()`                    |
| `onclick`属性じゃダメなの？                                        | 構造とふるまいが混ざる。`addEventListener()`なら複数登録できる         |
| `style.display`で直接書き換えたらダメ？                            | 動くが見た目の定義がJS/CSSに分散する。`classList`ならCSS側に集約できる |

### カテゴリ2：カリキュラム対象外の技術的質問 → **触れる程度に留める**

`docs/trainer_workshop_content.md` B項目が該当。**1分以内で理由を伝え、深追いしない**のが鉄則。個別にもっと聞きたい受講生には休憩時間・放課後に対応する旨を伝える。

| 想定質問                                          | 対応の芯                                                                         |
| ------------------------------------------------- | -------------------------------------------------------------------------------- |
| 親要素にリスナー1つでいいのでは？（イベント委譲） | その発想は正しい。ただし`event.target`での判別は今回のゴールを超えるので触れない |
| `aria-*`属性は付けなくていい？                    | 重要性は認めるが、今回はJS実装そのものに集中する設計                             |
| 配列やテンプレートリテラルでカードを生成できる？  | できるが今回の課題の範囲外（プログラミング色が強すぎる）                         |

### カテゴリ3：「動かない」系の質問（デバッグ依頼） → **拾う（下記コードレビューTipsで対応）**

このカテゴリが最も時間を取られやすく、かつ経験によって速度が変わる部分。詳細は次章。

### カテゴリ4：発展・アレンジ相談（「タブも作りたい」等） → **半分拾う（概要のみ）**

「取得→クリック→`classList`」の型の応用でできる、という点だけ伝えて、実装は今回の時間内ではやらない。余力があれば個別対応。

### カテゴリ5：進捗・自信に関する相談（「自分は全然できていない」） → **拾う（技術ではなく安心材料で対応）**

[[project_js_lesson_curriculum]]のA/B/Cレベル分けの考え方を伝える。「全員が3動き全部を自力完成させることを目標にしていない」「まず完成例が動けば十分」という前提を共有し、個別の技術指導よりも安心させることを優先する。

## コードレビューのTips（詰まりを素早く見つける）

タイプミスやコードの不備を素早く見つけるのは場数がものを言う部分だが、以下の**着眼点の順番**を型として渡せば、初回でもある程度の速度で対応できる。

**講師・完成版のコードとの間違い探しをしないこと。**受講生本人が原因を特定できる力を養うのが目的であり、以下の手順で診断する。

### 進め方の型（5ステップ）

1. **コンソールを開かせる**：無言でコードを目で追うより、エラーメッセージを一緒に読む方が速い。エラーが出ていなければ「そもそも実行されていない」（`<script>`の読み込み忘れ・位置）を疑う
2. **「型」のどのステップで詰まっているかを特定する**：教材はすべて「取得→クリック→`classList`（または属性コピー）」の型。まずこの3ステップのどこで止まっているかを本人に言わせる
3. **HTML側のクラス名／id名とJS側のセレクタを並べて見比べる**：タイポの大半はここ（詳細は下表）
4. **`console.log()`で「そもそも要素が取れているか」を確認させる**：`null`が返っていれば参照ミス、正しく取れているのにクリックしても動かなければイベント登録側を疑う、と切り分ける
5. **全部を教えずに、本人にコードを声に出して読ませる**：読み上げる過程で本人が気づくことが多い。答えを先に言わない

**実際に確認できるサンプル**：`materials/trainer_workshop/debug_practice/`（`index.html`）に、下表の①〜⑥それぞれに対応する意図的なバグ入りの実装を用意した。コンソールを開いて実際に挙動を確認しながらこの表を使うと理解が早い。

### よくあるミスパターン一覧

| ミス                                                       | 症状                                           | 見分け方                                           |
| ---------------------------------------------------------- | ---------------------------------------------- | --------------------------------------------------- |
| class名のスペルミス（HTML／CSS／JSで表記ゆれ）             | クリックしても何も起きない                     | `console.log(取得した変数)`→`null`                  |
| `.`や`#`の付け忘れ                                         | 同上                                           | セレクタの先頭を確認                                |
| `querySelector()`と`querySelectorAll()`の混同              | 1件しか動かない／全部同時に変な動きをする      | 対象が複数かどうかを確認                            |
| イベント名のtypo（`'click'`のつもりが`'onclick'`と書く等） | エラーは出ないが無反応                         | `addEventListener()`の第一引数を確認                |
| `<script>`タグの読み込み忘れ・位置ミス                     | コンソールにエラーすら出ない（そもそも未実行） | ネットワークタブ／`<script>`の有無を確認            |
| `classList`は切り替わっているのに見た目が変わらない        | JSは動いているがCSS側が対応していない          | devtoolsでクラスの付与を確認→CSS側のルールを確認    |

対象外にした項目：`forEach()`内で`break`しようとしてエラーになるケース（今回は範囲対象外）。
