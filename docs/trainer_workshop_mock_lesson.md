# 8/25 育成講師向け研修 模擬授業パート（ミニティーチング＋問答）想定質問集

> `docs/trainer_workshop_brief.md`「② 模擬授業①②③（問答形式）」で使う、トレーナー（私）側の割り込み質問の準備。
> 全部使う必要はなく、出野先生・辻野先生の説明を聞きながら、理解度に応じて選んで投げかける。

## 使い方

**担当や質問内容は事前共有しない（ぶっつけ本番）**。教材は8/19〜21の3日間ですでに共有済みであり、`materials/finish/portfolio/`の完成版コードを見ながら教えてもらってよい（コードを暗記して再現できるかではなく、見ながらでも理解して説明できるかを見る）。

①②は「短い説明（2分）→**ライブコーディング**（3分、完成版コードを見ながらでよいので実際に打つ／説明する）→問答」の構成、③は「説明（3分）→問答」のみ。ライブコーディング中も気になった時点で割り込んでよい（変数名の付け方の意図など）。説明・実演が終わったら、まず**核心を突く質問**を1つ投げ、答えの深さを見て次にどの質問を重ねるかを判断する。「わかる」止まり（コードをなぞって読み上げるだけ）か「理解」（自分の言葉で言い換えられる、想定外の状況にも答えられる）かを見極めることが目的。

**ライブコーディングで見るポイント**（①②共通）：完成版を見ながらでも「なぜこの変数名にするか」「なぜこの位置にコードを置くか」を自分の言葉で説明できるか／見ながら打っているだけで内容を理解せずになぞっているだけではないか（問答での深掘りで判別する）。

## ① ドロワーメニュー（出野先生）

**該当コード**（`materials/finish/portfolio/js/drawer.js`）
```js
const bodyElm = document.querySelector('body');
const btnNav = document.querySelector('#btn-nav');

btnNav.addEventListener('click', () => {
  bodyElm.classList.toggle('is-open');
});

const navLinks = document.querySelectorAll('.g-nav__link');

navLinks.forEach((link) => {
  link.addEventListener('click', () => {
    bodyElm.classList.remove('is-open');
  });
});
```

| # | 質問 | 見極めポイント |
|---|---|---|
| 1 | なぜ`body`に`is-open`を付けているんですか？ハンバーガーボタンやナビ自体に付けない理由は？ | CSS側で`.is-open`を起点に子孫要素の表示を制御する設計だと説明できるか |
| 2 | `toggle()`ではなく`add()`/`remove()`で書いたらどう変わりますか？ | 開閉状態を自分で判定するロジックが別途必要になる、と気づけるか |
| 3 | メニューを開いたままリンクをクリックしたらどうなりますか？なぜそう動きますか？ | `navLinks`の`forEach()`で各リンクにリスナーが付いていて`remove('is-open')`が呼ばれる、と辿れるか |
| 4 | リンクは複数あるのに、なぜ`querySelector()`ではなく`querySelectorAll()`を使うんですか？ | A-1の内容と接続して即答できるか |
| 5 | これをイベントバブリングで書き直すなら、どこにリスナーを付けますか？ | `.g-nav`に1つ付けて`event.target`で判別、とB-1の内容に接続できるか（できなくても大きな問題ではないが、余力チェックとして） |

## ② モーダルの属性値コピー（辻野先生・最大の難所）

**該当コード**（`materials/finish/portfolio/js/modal.js`）
```js
const worksImages = document.querySelectorAll('.works-card__img>img');
const dialog = document.querySelector('.works-dialog');
const dialogImage = document.querySelector('.works-dialog__img');
const dialogCloseBtn = document.querySelector('.works-dialog__close-btn');

worksImages.forEach((image) => {
  image.addEventListener('click', () => {
    dialogImage.src = image.src;
    dialogImage.alt = image.alt;
    dialog.showModal();
  });
});

dialogCloseBtn.addEventListener('click', () => {
  dialog.close();
});
```

| # | 質問 | 見極めポイント |
|---|---|---|
| 1（核心） | なぜ`dialogImage.src = image.src`と書くだけで、クリックした画像がモーダルに表示されるんですか？ | A-4の核心。クロージャで`image`（クリックされた画像）にアクセスでき、`dialogImage`（共通のモーダル画像）へ値をコピーしていると説明できるか |
| 2（深掘り） | `image`は`forEach()`の中でしか定義されていないのに、クリックイベントが起きた（ずっと後の）タイミングでどうしてまだ使えるんですか？ | 「関数は定義時のスコープを覚え続ける」というクロージャの本質に触れられるか |
| 3（誤答誘発） | じゃあ全部の画像で同じ`image`という変数を見ているということですか？ | 誤り訂正できるか。`forEach()`が1回呼ばれるたびに、その回専用の`image`が新しく作られる点を区別できるか |
| 4（境界） | 3枚目の画像をクリックした後、1枚目をクリックしたら、モーダルの中身はどうなりますか？なぜですか？ | `dialogImage`は1つしかない共有物なので単純に上書きされる、と説明できるか |
| 5（設計判断） | なぜ閉じるボタンの処理には、画像を初期化するコードがないんですか？ | 次に開くときにまた代入されるのでリセット不要、という実務的な思考ができるか（正解を当てさせるより、考え方を引き出す質問） |
| 6（代替実装） | これをイベントバブリングで書き直すとしたら、`image`の代わりに何を使いますか？ | `event.target`（や`closest()`）。B-1のコード例と接続できるか |
| 7（受講生役シミュレーション） | （受講生のふりをして）先生、`image.src`って何が入ってるんですか？画像そのものが入ってるんですか？ | 画像のURL（文字列）が入っているだけで画像データそのものではない、という基礎を平易に説明し直せるか |

**このパートで特に見たいこと**：feedback_2026-08.mdの「つまずきの原因は抽象度の異なる操作だから」という見立てが妥当か。辻野先生の説明が詰まる/曖昧になる箇所があれば、それが実際の受講生のつまずきポイントと一致するかもメモしておく。

### フィードバック観点（2026-08-24整理）

feedback_2026-08.mdの見立て（図解強化で足りるか／説明の仕方自体の指導が要るか）を判定するための観察軸。

| 軸 | 見るもの | 対応する質問 |
|---|---|---|
| 1. 概念の正確さ | `image.src`が何を指すか、クロージャの仕組み（なぜ後から`image`を使えるか）を自分の言葉で説明できるか | 質問1・2・3 |
| 2. 説明の順序・具体性 | いきなりコードを読み上げるのではなく、「クリックした要素の情報をモーダル側にコピーする」という概念レベルの説明を先に置けているか。比喩や図的な言葉を使えているか | 説明パート全体（問答前の2分間） |
| 3. 問答での対応力 | 想定外の質問（質問4・6・7）に対し、暗記知識の切り貼りでなく、その場で筋の通った答えを組み立てられるか | 質問4・6・7 |

**判定ロジック**：

| 軸1（概念） | 軸2（伝え方） | 軸3（応用） | 見立て |
|---|---|---|---|
| 強い | 弱い | 強い | 理解はしているが伝え方が下手 → **図解強化で対応可能**（feedback_2026-08.mdの当初方針どおり） |
| 弱い | – | 弱い | 辻野先生自身の理解に穴がある → **図解だけでは解決しない、説明の仕方自体の指導が必要** |
| 強い | 強い | 強い | そもそも難所ではなかった可能性 → 受講生側の他要因（前提知識・集中力等）を疑う |

軸1が弱い場合は図解を強化しても意味が薄い（説明する本人が理解していないものは図解しても伝わらない）ため、**軸1を最優先で見る**。
